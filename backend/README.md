# Cramberry Backend (C++ / Drogon)

The folder layout follows the Development View. Each module has a **repository** (storage), a **controller** (use-case logic, no HTTP) and a **Routes** file (the thin [Drogon](https://github.com/drogonframework/drogon) REST layer).

| Folder | What it holds |
| :--- | :--- |
| `user/` | Accounts, sign-in sessions, password hashing (FR-1, FR-2, FR-14) |
| `tasks/` | Courses, assignments, exams, status, filters, weekly report (UC-13, UC-14) |
| `schedule/` | Accepted study schedule, sharing, moving blocks, `.ics` export, dashboard (UC-4, UC-6, UC-8, UC-9) |
| `agent/` | Gemini client, local fallback planner, schedule generation, chatbot (UC-5, UC-7, UC-12) |
| `settings/` | Study preferences (UC-15) |
| `notifications/` | Notification settings, deadline reminders, in-app inbox (UC-16) |
| `data-api/` | `Database` and `Transaction`, the only code that talks to the database |
| `common/` | JSON shapes and HTTP helpers shared by the routes |

The test cases themselves are written up in [`docs/testing/JA_Test_Cases.md`](../docs/testing/JA_Test_Cases.md) and [`docs/testing/AA_Test_Cases.md`](../docs/testing/AA_Test_Cases.md).

### AA modules (Ahnaf Adib)

| Module | Use case | Purpose |
| :--- | :--- | :--- |
| `api/SchedulingRequestController` | UC-10 | `POST /api/schedule`: validates tasks, deadlines and preferences, then forwards the request to the Schedule System. |
| `api/StudentDataController`, `data/StudentDataRepository.h` | UC-11 | `GET`/`POST`/`PATCH /api/data`: saves, retrieves and updates a student's records after checking they own them. |
| `agent/ScheduleGenerationService` | UC-12 | Asks Gemini for a schedule, checks the JSON reply (fields, times, deadlines, overlaps) and saves it; keeps the old schedule if anything fails. |
| `schedule/SchedulingTypes.h` | Shared | Date/time parsing and the types passed from UC-10 to UC-12. |

UC-12 uses [nlohmann/json](https://github.com/nlohmann/json) v3.11.3, which CMake downloads on the first configure along with GoogleTest.
The database is **Supabase PostgreSQL** in production and **SQLite** for local development and tests. The SQL is identical for both. Every query is scoped to the signed-in student's ID, which comes from the session token, never from the request (NFR-19).

When `OPENROUTER_API_KEY` or `GEMINI_API_KEY` is set, schedules are generated by an AI model: Claude Haiku 5.5 through OpenRouter by default (any OpenRouter model via `OPENROUTER_MODEL`), or Gemini through Google's API. OpenRouter wins if both are set. Every proposal is checked against the student's preferences (`validateNKSchedule` + `findPreferenceViolations`). If the AI fails, is not configured, or breaks a rule, a deterministic local planner is used instead, so AI outages never stop planning (NFR-15). Every attempt is logged in `generation_runs`.

## Build and run

You need CMake 3.20+, a C++20 compiler and [vcpkg](https://github.com/microsoft/vcpkg). The dependencies are listed in [`vcpkg.json`](vcpkg.json) and installed automatically the first time you configure (the first time takes about 5 minutes).

```bash
cmake -S backend -B backend/out/build -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake
cmake --build backend/out/build --config Debug
ctest --test-dir backend/out/build -C Debug --output-on-failure
```

Without the vcpkg toolchain, CMake still builds and runs the use-case tests (`cramberry_tests`), but skips the server.

To connect to Supabase, also configure with `-DVCPKG_MANIFEST_FEATURES=supabase` (this builds libpq).

Start the server:

```bash
backend/out/build/Debug/cramberry_server        # http://127.0.0.1:8080
```

| Environment variable | Default | Purpose |
| :--- | :--- | :--- |
| `CRAMBERRY_DATABASE_URL` | *(unset → SQLite)* | Supabase/PostgreSQL connection string |
| `CRAMBERRY_SQLITE_PATH` | `cramberry.db` | SQLite file for local development |
| `OPENROUTER_API_KEY` / `OPENROUTER_MODEL` | *(unset)* / `anthropic/claude-haiku-5.5` | Enables AI schedules and the chatbot through OpenRouter |
| `OPENROUTER_REASONING` | `0` | `1` lets the model reason before answering: slower and costlier |
| `GEMINI_API_KEY` / `GEMINI_MODEL` | *(unset)* / `gemini-2.5-flash` | Same, through Google's Gemini API |
| `CRAMBERRY_HOST` / `CRAMBERRY_PORT` | `127.0.0.1` / `8080` | Listen address |
| `CRAMBERRY_CORS_ORIGIN` | *(unset)* | Frontend origin, e.g. `http://localhost:3000` |
| `CRAMBERRY_AUTO_REPLAN` | `1` | Re-plan in the background after task or preference changes |
| `CRAMBERRY_THREADS` / `CRAMBERRY_WORKERS` | `4` / `4` | HTTP threads / worker threads for slow work |

## REST API

**Full reference: [API.md](API.md)**. It covers request and response shapes, validation rules, status codes and examples. The summary below lists the endpoints.

Every route except register, login and health needs `Authorization: Bearer <token>`. Errors look like `{"error": "...", "details": [...]}`. Times are ISO 8601 UTC (`2026-12-01T23:59:00Z`). Weekly study hours and blocks use `{"day": "Mon", "start": "16:00", "end": "19:00"}` in the student's local time (set with `utcOffsetMinutes`).

| Method and path | Purpose |
| :--- | :--- |
| `POST /api/auth/register` `{name, email, password, utcOffsetMinutes?}` | Create an account, returns `{token, student}` |
| `POST /api/auth/login` `{email, password}` / `POST /api/auth/logout` | Sign in / out |
| `GET`, `PATCH`, `DELETE /api/users/me` | Profile; delete needs `{password}` |
| `GET`, `POST /api/courses`, `PATCH`, `DELETE /api/courses/{id}` | Courses |
| `GET /api/tasks?courseId=&from=&to=&status=&overdue=true` | List and filter tasks |
| `POST /api/tasks`, `GET`, `PATCH`, `DELETE /api/tasks/{id}` | Task CRUD (`type`: assignment, exam, study, other; `priority` 1-3) |
| `PUT /api/tasks/{id}/status` `{status}` | `NOT_STARTED`, `IN_PROGRESS`, `COMPLETED` |
| `GET /api/reports/weekly?start=YYYY-MM-DD` | Completed, overdue and remaining tasks this week |
| `GET`, `PUT /api/settings/preferences` | Study preferences (409 if personal time clashes with the schedule) |
| `GET`, `PUT /api/settings/notifications` | Notification settings |
| `GET /api/notifications?unread=true`, `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all` | In-app inbox |
| `POST /api/agent/generate` `{day?}` | Generate this week's (or one day's) plan |
| `POST /api/agent/chat` `{message}` | Ask the AI assistant (503 without Gemini) |
| `GET /api/agent/runs` | Recent generation attempts |
| `GET`, `DELETE /api/schedule`, `PATCH /api/schedule/blocks` | View, clear, or move a block |
| `GET /api/schedule/export.ics` | Download the plan and deadlines as iCalendar |
| `POST`, `GET /api/schedule/shares`; `DELETE /api/schedule/shares/{shareId}` | Share with a registered recipient, list, or revoke access |
| `GET /api/schedule/shared-with-me`, `GET /api/schedule/shared-with-me/{shareId}` | List shared schedules and view the latest shared schedule |
| `GET /api/dashboard` | Today's blocks, upcoming and overdue tasks, counts |
| `GET /api/health` | Database and AI status |

## Known limits

- Email and SMS reminders are stored in the in-app inbox and logged. Delivering them needs a provider plugged into `InboxGateway`.
- Reminder de-duplication is held in memory, so restarting the server can resend a reminder that is still inside its window.
- Time zones are fixed UTC offsets, with no daylight-saving rules.
- Shared schedule views fetch the owner's latest schedule on each API request. Push-based live refresh in a frontend client is not implemented.
- MFA (FR-5) and syllabus upload (UC-3) are not implemented yet.
